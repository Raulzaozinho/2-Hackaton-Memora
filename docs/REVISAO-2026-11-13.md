# Revisão da Feira Dev — 13/11/2026

O projeto foi revisado e executado no Windows. A plataforma, a barraca modelo e o ensaio
do evento estão funcionando nos cenários abaixo. As barracas das equipes continuam
como exercícios, de acordo com os cartões das quatro rodadas.

## Correções realizadas

- **Limite de fichas:** o teste reproduziu dez votos aceitos para uma pessoa que só tinha cinco.
  As operações de dar e devolver fichas agora bloqueiam o registro da pessoa durante a transação.
  Dez requisições simultâneas passaram a aceitar exatamente cinco votos.
- **Inicialização:** consultas ao servidor não criam mais o evento enquanto os crachás estão
  sendo carregados. Durante esse intervalo a API responde 503 e a interface tenta novamente.
  Um ensaio com vinte consultas concorrentes não produziu erros de integridade.
- **Demonstração:** usa apenas pessoas fictícias, mesmo se o projeto já tiver crachás reais.
  O script impede combinar os modos demo e Supabase.
- **Organização:** o placar privado acompanha a votação automaticamente.
- **Troca de pessoa:** respostas atrasadas de consultas e votos não substituem o saldo do
  crachá escolhido depois. Os temporizadores são encerrados quando o serviço é destruído.
- **Rodízio:** quem retorna a uma equipe entra no fim da ordem, mesmo se alguém saiu antes.
  Selecionar novamente a mesma equipe preserva a posição.
- **Premiação:** pontuações iguais dividem a posição. O telão mostra o empate sem escolher
  uma campeã pela ordem de cadastro; o layout foi conferido em 1280 × 720.
- **Entregas:** o front compila em uma pasta separada e só é publicado depois da validação.
  O index é trocado por último, mantendo os bundles anteriores para telas ainda abertas.
  Falhas de inicialização restauram o jar anterior. Erros de Git e de registro de entregas
  são informados, renomeações não contornam a restrição de pastas e uma porta ocupada
  não é confundida com um servidor recém-iniciado.
- **Documentação e CI:** instruções de ensaio atualizadas, testes do telão adicionados ao
  workflow e PIN de exemplo preenchido com o padrão documentado.

O bloqueio de banco utiliza o mecanismo de
[@Lock do Spring Data JPA](https://docs.spring.io/spring-data/jpa/reference/3.5/jpa/locking.html).

## Como repetir

Com Node/npm e JDK instalados, na pasta frontend:

```bash
npm ci
npm test -- --watch=false
npm run build
```

Na pasta backend: `./mvnw verify` ou `.\mvnw.cmd verify` no Windows.
Na raiz: `node --test scripts/telao.test.mjs`.
Para ensaiar: `node scripts/telao.mjs --demo`.

Nesta máquina, na pasta original revisada, o arquivo **ABRIR-DEMO-LOCAL.cmd** também inicia
o ensaio usando o Java e o Node encontrados. Ele depende dessas instalações locais e
da pasta .tools; não faz parte do pacote de código para outras máquinas.

Os logs, resultados JSON, imagens e roteiros usados na revisão estão em **.validation**
na pasta original. Essa pasta e as ferramentas locais são ignoradas pelo Git.

- **Supabase real:** não foi configurado nem acessado; não havia backend/.env com as credenciais.
  Os testes de banco usaram H2 no modo PostgreSQL. É necessário ensaiar com o Supabase antes do evento.
- **GitHub real:** esta pasta não era um repositório Git. O acompanhamento foi validado com um
  remoto Git local, sem criar repositório externo nem fazer push para contas reais.
- **Rede e aparelhos:** o navegador simulou o tamanho de celular; Wi-Fi, firewall, celular físico
  e projetor da sala precisam do ensaio indicado no guia da organização.

O projeto está validado para o ensaio local. Esses três itens ainda precisam ser verificados
para confirmar a operação no ambiente do evento.

## Segunda conferência, no mesmo dia

Uma conferência independente repetiu tudo em uma cópia limpa do projeto, em outra porta:
os 12 testes do back-end, os 10 do front-end, a compilação de produção e os testes do script
do telão passaram. O acompanhamento de entregas foi refeito com um remoto Git local e
compilações reais, usando como entrega o código exato dos cartões das quatro rodadas:

| Entrega simulada | Resultado |
|---|---|
| Barraca completa seguindo os cartões (front e back) | Aceita; lista, formulário e sorteio funcionando no navegador |
| Erro de sintaxe no Java | Recusada, com arquivo e linha no telão |
| Alteração fora da pasta da equipe | Recusada antes de compilar |
| Java que compila, mas tem dois métodos no mesmo endereço | Recusada; a versão anterior voltou ao ar sozinha |

Três ajustes saíram dessa conferência:

- **Motivo da falha ao subir:** quando um back-end compila mas não inicia, o telão agora diz
  por quê (por exemplo, "dois métodos respondem em GET /api/barracas/equipe-2/itens"). Antes
  mostrava só que não iniciou. O terminal do telão também ficou mais limpo: o que o servidor
  escreve durante a subida só aparece se ela falhar.
- **Fim de linha:** o arquivo `.gitattributes` na raiz faz todos receberem os arquivos com o
  mesmo fim de linha. Sem ele, uma máquina com outra configuração do Git podia marcar arquivos
  inteiros como alterados, e a entrega seria recusada por "mexer fora da pasta".
- **Cola de Git:** ganhou a linha do quarto motivo de recusa ("compilou, mas não iniciou").
